# Design notes: interpretations and deviations

These are the places where the written specification left room, and what was decided.

1. **"Critical" incidents.** The dashboards count an incident as critical when it is an **open P1**. The overview also reports `critical_total` (all P1 ever).
2. **Re-assignment.** The lifecycle diagram has no arrow back to ASSIGNED, but the service desk needs to reassign work. An admin may reassign while the incident is ASSIGNED, ACKNOWLEDGED or IN_PROGRESS. The status becomes ASSIGNED again, the previous technician is notified and the event is audited. Technicians cannot do this.
3. **Admin override.** Assigning a technician who lacks the skill, is unavailable or is over the workload limit needs an explicit override flag, shown in the UI as a confirmation, and recorded in the audit log. This satisfies "never silently assign without the required skill".
4. **Library choices.** Passwords use the `bcrypt` package directly and tokens use `PyJWT`, instead of passlib and python-jose, because those two are actively maintained and have no known incompatibilities with current Python versions.
5. **Score 39.** With ratings of 1 to 5 the product 39 cannot occur (39 = 3 x 13). The boundary is still tested through `PriorityStrategy.level_for_score`, so T06 is verified at the level of the algorithm.
6. **Duplicate detection** looks at incidents created in the last 7 days. It never blocks, merges or closes anything. An admin may manually link an incident as related.
7. **Information requests** do not pause the SLA clock. The assignment does not define a pause rule, so the conservative choice was made.
8. **Simulated e-mail** is stored in the `notifications` table with channel `EMAIL` and also written to the server log. The admin "E-mail outbox" screen reads it. A real SMTP channel would be another `NotificationChannel` subclass.
9. **Demo data** is generated through the real services with a moved clock, so its audit rows, notifications and SLA violations are genuine, not hand-inserted.
10. **Reset of time-based demo state.** SLA states in the demo data are relative to the first start. Restarting later makes open demo incidents progressively more overdue, which is realistic.
11. **Testing limits.** The browser walkthrough was run once by hand scripting (login, report, assign, acknowledge, investigate, information request and reply, resolve, verify, feedback, close, override assignment). There is no automated frontend test suite.
12. **Affected users and priority.** The assignment lists "number of affected users" as an input but gives no formula. The original design stored it for information only. The rule is now explicit: large counts raise the *counted* impact to a floor (10 users: 2, 50: 3, 250: 4, 1000: 5), never lower it, and the reporter's own impact stays stored beside the effective one. The thresholds are constants in `AffectedUsersPolicy`, the rule is audited, and an administrator can disable it in Settings. The existing P1 to P4 bands and every earlier test are unchanged, because incidents without a count behave exactly as before.
13. **Audit triggers.** Append-only audit is enforced by ORM listeners in the running application. The two SQLite triggers exist only in `database/schema.sql` as optional hardening for a hand-built database.
14. **Diagram accuracy.** Class, ER, architecture and use case diagrams are generated from the code and checked by `docs/tools/verify_diagrams.py`. Which classes appear in each view, and which links are drawn as composition, aggregation or dependency, are curated and verified, not inferred. The first verification run found five inaccuracies in the curated edges, now fixed (see `DIAGRAM_VERIFICATION.md`).
